
HCI-проект интернет-аптеки: практическое руководство, архитектура артефактов и МЕГА-ПРОМПТ
Что именно должен доказывать ваш проект
Ваш проект лучше воспринимать не как «нужно нарисовать красивый сайт аптеки», а как демонстрацию того, что команда умеет проектировать взаимодействие человека с системой в условиях реальных ошибок, ограничений и неопределённости. Это хорошо соответствует human-centred design: ISO 9241-210:2019 требует строить процесс проектирования вокруг понимания пользователей, их задач и контекста использования, вовлекать пользователей в дизайн и оценку и итеративно улучшать решение на основании обратной связи. Актуальная редакция ISO 9241-210:2019 была повторно подтверждена ISO в 2025 году.

Поэтому сильная работа выглядит не так:

Пользователь → товар → корзина → оплата → готово.

А так:

Пользователь пытается выполнить конкретную задачу → система постоянно показывает, что происходит → предотвращает ошибки там, где может → обнаруживает ошибки → объясняет их понятным языком → сохраняет уже введённые данные → предлагает безопасный путь восстановления → никогда не изображает успех, пока он реально не подтверждён.

Последняя часть особенно важна для аптеки и платежей. Nielsen Norman Group выделяет видимость состояния системы, предотвращение ошибок, распознавание вместо запоминания и помощь пользователю в восстановлении после ошибки как фундаментальные эвристики UX.

Ваш сценарий — адаптивный сайт интернет-аптеки для быстрой покупки и доставки лекарств человеку, которому плохо и который не хочет или не может идти в аптеку. Это означает, что интерфейс должен проектироваться для пользователя, у которого потенциально снижены внимание, энергия и терпение. В интерфейсе особенно важны короткие шаги, понятные подписи, отсутствие лишней памяти и однозначные сообщения об ошибках; W3C отдельно рекомендует ясные пошаговые инструкции и подчёркивает, что серия сложных ошибок может полностью сорвать выполнение задачи для человека с когнитивными ограничениями.

При этом учебный проект не должен притворяться полноценной медицинской системой. Не стоит реализовывать «ИИ ставит диагноз», «препарат точно вам подходит» или «рецепт автоматически одобрен». В реальных онлайн-аптеках законность продажи препаратов, требования к рецептам, лицензированию и работе фармацевта зависят от юрисдикции. WHO отмечает, что в ряде стран онлайн-покупка лекарств разрешена через должным образом авторизованные аптеки и с рецептом там, где он требуется, но одновременно предупреждает о большом количестве нелегальных продавцов и фальсифицированных препаратов.
 FDA приводит аналогичные требования для США, но они относятся именно к американской юрисдикции и не должны автоматически переноситься на другую страну.

Для вашей презентации можно сформулировать цель так:

«Спроектировать доступный, отказоустойчивый и понятный сервис быстрой покупки аптечных товаров, который помогает пользователю успешно завершить заказ даже при ошибках оплаты, отсутствии товара, проблемах сети, адреса и доставки, при этом явно отделяя подтверждённые системой факты от предположений и соблюдая ограничения, связанные с рецептурными товарами и персональными данными».

Это звучит значительно профессиональнее, чем просто «сайт для доставки лекарств».

Как связаны Task Flow, User Flow и BPMN
Эти три артефакта похожи, поэтому студенты часто делают три одинаковые блок-схемы. Так делать не стоит.

Task Flow отвечает на вопрос: «Какие действия нужны, чтобы выполнить конкретную задачу?»

Он обычно описывает один основной сценарий и концентрируется на последовательности действий. Например, задача «Заказать безрецептурное средство с доставкой»:

text
Копировать
Найти препарат
↓
Открыть карточку
↓
Проверить наличие и цену
↓
Добавить в корзину
↓
Указать адрес
↓
Выбрать доставку
↓
Выбрать способ оплаты
↓
Проверить заказ
↓
Подтвердить
↓
Получить подтверждение заказа
Task Flow полезно делать первым, потому что он заставляет команду определить саму задачу без перегрузки всеми возможными системными событиями.

User Flow отвечает уже на более широкий вопрос: «Какими путями пользователь может двигаться через интерфейс и что происходит после каждого решения?»

Здесь появляются экраны, решения, возвраты и error states:

text
Копировать
Поиск
↓
Есть результаты?
├─ Да → Карточка товара
│       ↓
│      Есть в наличии?
│       ├─ Да → Добавить в корзину
│       └─ Нет → Аналоги / уведомление / назад к поиску
│
└─ Нет → Исправить запрос / категории / обратиться за помощью
То есть Task Flow — это преимущественно логика выполнения задачи, а User Flow — навигация пользователя через продукт с развилками и экранами.

Термины Task Flow и User Flow не стандартизированы так строго, как BPMN, поэтому конкретные определения могут немного различаться между преподавателями, UX-командами и инструментами. Для учебного проекта важнее один раз определить вашу нотацию и дальше использовать её последовательно.

BPMN — уже не просто UX-схема. Она показывает бизнес-процесс и взаимодействие участников и систем. Актуальной формальной спецификацией OMG является BPMN 2.0.2.

Для вашего преподавательского требования user / service / script лучше использовать следующую интерпретацию.

Что мог иметь в виду преподаватель	Как лучше показать
User	Lane или Pool «Покупатель»
Service	«Аптека / сервис доставки / платежный сервис / оператор»
Script	Автоматизированные действия системы
System	Web App / Backend / Inventory / Order Service

Ключевая тонкость: script в BPMN обычно лучше не трактовать как отдельного человеческого участника. Если речь идёт об автоматизации, логичнее сделать lane System / Backend и внутри него ставить автоматизированные задачи. Если преподаватель буквально требует три дорожки User / Service / Script, можно сохранить эти подписи в учебной версии, но рядом дать пояснение:

Script/System = автоматизированные действия приложения и backend без участия человека.

Для более профессиональной BPMN можно использовать такие swimlanes:

text
Копировать
POOL: Online Pharmacy

Lane: User
Lane: Web UI
Lane: Backend / Order Service
Lane: Inventory / Pharmacy
Lane: Payment Provider
Lane: Delivery Service
Если внешний участник является самостоятельной организацией или системой, BPMN допускает представлять его отдельным Participant/Pool; взаимодействие между участниками моделируется сообщениями.

Самая важная идея: Task Flow показывает задачу, User Flow показывает UX-пути, BPMN показывает, кто и что реально делает за интерфейсом.

Например, одно нажатие пользователя:

«Оплатить»

в User Flow может выглядеть как один переход:

text
Копировать
Checkout → Processing → Success
а в BPMN превращается в цепочку:

text
Копировать
User:
Нажимает «Оплатить»

Web UI:
Блокирует повторное нажатие
Показывает Processing

Backend:
Создаёт payment attempt

Payment Provider:
Авторизует / отклоняет / возвращает unknown status

Backend:
Проверяет результат

Gateway:
Успех?
├─ Да → создать заказ
├─ Нет → вернуть причину отказа
└─ Unknown → проверить статус операции
Именно такое различие показывает преподавателю, что команда понимает HCI не только как набор экранов.

Что обязательно учесть с точки зрения HCI
Базовый HCI-фреймворк для проекта удобно построить вокруг ISO 9241-210, Nielsen heuristics, WCAG 2.2 и тестирования реальных задач. ISO требует human-centred и итеративный процесс, а не одноразовое рисование интерфейса.

Состояние системы должно быть всегда понятно. Пользователь должен видеть разницу между:

text
Копировать
Загрузка…
Проверяем наличие…
Проверяем адрес…
Переходим к оплате…
Оплата обрабатывается…
Заказ создан.
Не удалось подтвердить оплату.
Не удалось определить статус оплаты.
Нельзя использовать один универсальный spinner для всех операций. Nielsen прямо связывает видимость системного состояния с предсказуемостью интерфейса и доверием пользователя.

Особенно опасен экран:

text
Копировать
Оплата прошла успешно!
если backend получил timeout и фактически не знает результата платежа.

Правильнее:

Проверяем статус оплаты. Не повторяйте платёж.

а затем запросить подтверждённый статус у платёжной системы.

Для предотвращения повторных списаний платежные API могут использовать идемпотентность: Stripe, например, описывает idempotency keys как механизм, позволяющий безопасно повторить запрос после сетевого сбоя, не выполняя побочный эффект дважды. Это не означает, что вашему MVP нужен настоящий Stripe; это полезная системная модель для BPMN и архитектуры.

Ошибки должны быть конкретными и исправимыми. WCAG 2.2 требует, чтобы автоматически обнаруженная ошибка была идентифицирована и описана текстом; на уровне AA также предусмотрены рекомендации по исправлению ошибки, если такая рекомендация известна.

Плохо:

Error 422.

Лучше:

Не удалось проверить адрес. Уточните номер дома или выберите адрес на карте.

Плохо:

Invalid card.

Лучше:

Банк отклонил оплату. Деньги нами не списаны. Вы можете попробовать другую карту или другой способ оплаты.

Если система не знает, было ли списание:

Мы пока не можем подтвердить результат платежа. Не оплачивайте повторно. Проверяем статус операции.

В формах следует сохранять уже введённые значения, а ошибки желательно показывать рядом с конкретным полем; W3C рекомендует доступную валидацию, а исследования Baymard показывают, что пользователи испытывают серьёзные затруднения, когда после отправки формы вынуждены искать ошибку или повторно вводить исчезнувшие данные.

Доступность должна быть частью проекта, а не приложением в конце. WCAG 2.2 является актуальной W3C Recommendation, и W3C рекомендует применять наиболее свежую версию стандарта; соответствие WCAG 2.2 также покрывает требования WCAG 2.1 и 2.0.

Для учебного проекта разумная цель:

WCAG 2.2 AA.

Практически это означает: достаточный контраст, текстовые labels для полей, навигацию клавиатурой, видимый focus, отсутствие информации только через цвет, корректные headings, доступные сообщения об ошибках, понятную последовательность Tab, alt-тексты там, где изображение несёт смысл, и увеличение интерфейса без разрушения layout. GOV.UK рекомендует проверять доступность как автоматизированными, так и ручными тестами, а также тестировать продукт с assistive technologies.

WCAG 2.2 также добавляет критерий минимального target size: для указателя базовое значение критерия составляет 24×24 CSS px с предусмотренными стандартом исключениями. Для мобильного проекта я бы проектировал основные CTA значительно крупнее минимального требования, особенно учитывая больного или уставшего пользователя.

Mobile-first здесь особенно оправдан как проектное решение. Основной critical path должен помещаться на небольшом экране без сложных таблиц, горизонтального скролла и мелких контролов:

text
Копировать
Поиск → товар → корзина → адрес → доставка → оплата → подтверждение
Причём mobile UX не должен быть «обрезанной desktop-версией». На телефоне особенно важны sticky summary/CTA без перекрытия keyboard focus; WCAG 2.2 требует, чтобы элемент в keyboard focus не был полностью скрыт авторским интерфейсом.

Цена и время должны быть прозрачными до последнего подтверждения. Пользователь должен до оплаты видеть:

text
Копировать
Товары
Доставка
Скидка
Итого
Ориентировочное время доставки
Адрес
Способ оплаты
Checkout — одна из наиболее чувствительных областей e-commerce UX. Многолетние исследования Baymard показывают, что проблемы структуры checkout, форм, payment flow, ошибок и сохранения данных способны приводить к отказу от заказа.

Аптечная специфика требует safety UX. Продукт не должен предлагать рецептурный препарат так, будто ограничений не существует. Для такого товара можно сделать состояние:

Для этого препарата может потребоваться рецепт. Требования зависят от законодательства вашей страны.

После этого сценарий:

text
Копировать
Проверка требований
↓
Нужен рецепт?
├─ Нет → checkout
└─ Да → предоставить допустимый документ / подтверждение фармацевта
Но UI не должен сам объявлять рецепт действительным, если это не подтверждено реальной системой.

WHO предупреждает, что сайты, продающие рецептурные препараты без предусмотренного требования рецепта, могут быть признаком небезопасной онлайн-аптеки, и рекомендует пользователям проверять авторизацию продавца там, где существует соответствующий механизм.

Конфиденциальность необходимо проектировать минималистично. Не спрашивайте диагноз, хронические заболевания или другие чувствительные данные, если они не нужны вашему сценарию. В юрисдикциях ЕС сведения о здоровье относятся к специальным категориям персональных данных по статье 9 GDPR и требуют отдельного правового основания и гарантий; это пример того, почему команда должна определить целевую юрисдикцию до реального запуска.

Для технического security checklist разумно использовать OWASP ASVS как ориентир: стандарт покрывает аутентификацию, сессии, access control, валидацию, data protection, API, error handling и другие категории безопасности веб-приложений.

Personas, сценарии, edge cases и recovery UX
Для учебного проекта достаточно нескольких контрастных персон, если каждая влияет на дизайн.

Persona A — Айжан, 22 года.

Температура, лежит дома, пользуется телефоном одной рукой. Хочет за несколько минут найти конкретный безрецептурный товар и заказать доставку.

Главные потребности:

text
Копировать
быстрый поиск
минимум текста
понятная цена
реальное наличие
минимум полей
быстрая оплата
понятный ETA
Persona B — Ерлан, 61 год.

Покупает лекарства с телефона, зрение хуже, боится ошибиться при оплате.

Для него особенно важны:

text
Копировать
крупные controls
понятные labels
не полагаться только на цвет
review перед оплатой
явные статусы
понятный recovery
контакт поддержки
Persona C — Мария, 34 года.

Покупает препарат родственнику. Не уверена, какой вариант формы/дозировки нужен, и сталкивается с рецептурным ограничением.

Для неё важны:

text
Копировать
различие между товарами
понятная информация о форме и дозировке
явное предупреждение о рецептурном ограничении
возможность получить помощь специалиста
никаких медицинских обещаний от интерфейса
Ключевой сценарий проекта лучше сделать таким:

Пользователь открывает сайт на телефоне → ищет конкретный препарат → видит карточку и наличие → добавляет в корзину → вводит адрес → система проверяет возможность доставки → показывает цену и ETA → пользователь выбирает оплату → подтверждает заказ → получает подтверждённый номер заказа → отслеживает статус.

Но оценивать HCI лучше по тому, насколько хорошо вы обработали не happy path, а альтернативы.

Ниже — хороший минимальный каталог исключений.

Ситуация	Что должна сделать система	Что показывать пользователю
Поиск ничего не нашёл	Не создавать тупик	«Ничего не нашли. Проверьте название или попробуйте категорию.»
Товара нет	Запретить добавление	«Сейчас нет в наличии» + безопасные варианты продолжения
Товар исчез после добавления в корзину	Повторно проверить stock перед checkout	«Товар закончился, пока был в корзине. Мы обновили заказ.»
Части количества нет	Уменьшить доступное количество только после объяснения	«Доступно 2 из 3.»
Аналогов нет	Не выдумывать замену	«Подходящих доступных вариантов не найдено.»
Медленная сеть	Сохранить контекст	Skeleton/loading + «Загружаем…»
Интернет пропал	Не уничтожать корзину	«Нет соединения. Корзина сохранена на этом устройстве.»
API timeout	Дать retry там, где он безопасен	«Не удалось получить ответ. Повторить?»
Server 500	Не показывать stack trace	«Сервис временно недоступен. Попробуйте ещё раз.»
Сессия истекла	Сохранить безопасно восстановимые данные	«Сессия завершилась. Войдите снова; корзина сохранена.»
Адрес пустой	Остановить checkout	Inline error
Адрес некорректен	Объяснить проблему	«Не удалось найти дом. Проверьте адрес.»
Район вне зоны доставки	Не принимать заказ	«По этому адресу доставка пока недоступна.»
Delivery API не отвечает	Не обещать срок	«Не удалось определить время доставки.»
Payment method недоступен	Disable/скрыть с объяснением	«Этот способ временно недоступен.»
Платёж отклонён	Заказ не считать оплаченным	Причина на понятном уровне + альтернативный способ
Пользователь закрыл payment flow	Вернуть в checkout	«Оплата не завершена.»
Payment timeout	Проверить статус	«Проверяем платёж. Не повторяйте оплату.»
Пользователь дважды нажал Pay	Не создавать два платежа	Disabled CTA + processing state
Был retry платежа	Использовать один payment intent/idempotency model	Не создавать второй заказ

В BPMN преподаватель упоминал:
User
Service
Script/System

Интерпретируй это профессионально.

User = действия человека.

Service = человеческий или внешний сервисный участник, например:
— pharmacy/operator;
— payment provider;
— delivery service.

Script/System = автоматизированные действия приложения/backend.

Если слово Script преподаватель использует буквально как отдельную дорожку, можно сохранить учебную дорожку Script/System, но обязательно поясни, что в полноценном BPMN автоматизированные операции обычно размещаются в lane системы, а конкретный тип automated/script/service task отражается типом BPMN task.

При необходимости предложи две версии BPMN:
A. Simplified teacher-friendly.
B. Professional BPMN 2.0-style.

========================================
ОБЯЗАТЕЛЬНЫЕ FAILURE / EDGE CASES
========================================

Проработай как минимум:

CATALOG / INVENTORY
— товар отсутствует;
— товар закончился после добавления в корзину;
— доступно меньше единиц, чем выбрал пользователь;
— цена изменилась;
— карточка товара временно недоступна;
— товар снят с продажи;
— подходящего аналога нет;
— аналоги существуют, но нельзя утверждать, что они медицински взаимозаменяемы без подтверждения специалиста.

SEARCH
— запрос ничего не нашёл;
— опечатка;
— слишком общий запрос;
— API поиска не отвечает;
— пустой запрос.

CART
— пустая корзина;
— товар недоступен;
— количество изменилось;
— данные корзины устарели;
— пользователь открыл корзину после долгого перерыва;
— корзина должна восстановиться после reload, если это возможно.

ADDRESS
— адрес не указан;
— адрес введён некорректно;
— дом не найден;
— адрес неоднозначный;
— доставка по адресу недоступна;
— пользователь изменил адрес после расчёта доставки.

DELIVERY
— нет доступных временных слотов;
— delivery API недоступен;
— ETA неизвестен;
— ETA изменился;
— курьер задерживается;
— курьер отменён;
— доставка стала невозможна после оформления;
— пользователь отменяет заказ.

PAYMENT
— способ оплаты недоступен;
— платёж отклонён;
— пользователь прервал оплату;
— сеть пропала во время оплаты;
— payment API timeout;
— payment provider вернул ошибку;
— пользователь дважды нажал Pay;
— браузер повторил запрос;
— произошёл retry;
— статус платежа неизвестен;
— платёж прошёл, но ответ потерялся;
— возможное двойное списание;
— refund initiated;
— refund pending;
— refund completed.

КРИТИЧЕСКОЕ ПРАВИЛО:
НИКОГДА не показывай PAYMENT SUCCESS, ORDER SUCCESS, REFUND SUCCESS, STOCK CONFIRMED или DELIVERY CONFIRMED, пока соответствующая система не вернула подтверждённый статус.

При payment timeout сначала показывай:
«Проверяем статус оплаты. Не повторяйте платёж.»

Проектируй идемпотентную модель платежа:
одна пользовательская попытка → один payment operation identifier / idempotency key.

Retry не должен создавать второй платёж.

NETWORK / SYSTEM
— медленный интернет;
— offline;
— timeout;
— API failure;
— server 500;
— maintenance;
— partial response;
— stale data;
— session expired;
— authentication failure.

FORMS
— обязательное поле пустое;
— неверный формат;
— ошибка отображается рядом с полем;
— error summary для сложной формы;
— данные не удаляются после ошибки;
— исправленная ошибка исчезает;
— фокус переводится логично и доступно.

PRESCRIPTION / MEDICATION SAFETY
— препарат может требовать рецепт;
— рецепт отсутствует;
— документ не читается;
— проверка pending;
— проверка rejected;
— требования неизвестны;
— пользователь пытается продолжить без необходимого подтверждения.

Не выдумывай законодательство.

Всегда говори:
«Точные требования зависят от юрисдикции и должны быть проверены по официальным нормативным источникам страны запуска.»

Не диагностируй заболевания.
Не назначай лекарства.
Не утверждай, что препарат подходит пользователю.
Не генерируй медицински опасные рекомендации.

========================================
TASK FLOW
========================================

Для Task Flow:

— определить одну пользовательскую цель;
— определить start;
— определить end;
— дать последовательность task-level действий;
— не перегружать экранами;
— показать normal/happy task;
— отдельно перечислить preconditions;
— success condition;
— failure points.

Выводить:

1. Goal
2. Actor
3. Preconditions
4. Trigger
5. Flow
6. Success criterion
7. Main failure points

Дать Mermaid-диаграмму.

========================================
USER FLOW
========================================

User Flow должен включать:

— screens;
— decisions;
— system feedback;
— alternative paths;
— failures;
— recovery;
— cancellation;
— return paths;
— end states.

Для каждого decision node обязательно показать обе/все ветки.

Например:

Stock available?
YES → Add to cart
NO → Out-of-stock state → alternatives / back to search.

Не допускай dead ends без следующего действия.

Выводить:

A. текстовую карту;
B. Mermaid flowchart;
C. таблицу Screen / Trigger / State / User Action / Next State;
D. список exception paths.

Web UI

Inventory / Pharmacy
Payment Provider
Delivery Service

Если внешний сервис логичнее отдельным Pool, скажи об этом.

Главный BPMN должен покрыть:

Search
→ Stock verification
→ Cart
→ Address validation
→ Delivery availability
→ Checkout
→ Payment
→ Order creation
→ Fulfilment
→ Delivery
→ Completion / cancellation.

Обязательно включить exception branches:

stock unavailable
address invalid
delivery unavailable
payment declined
payment unknown
server failure
session expiration
order cancellation
delivery delay.

После BPMN выдай:

— Mermaid approximation, если возможно;
— BPMN pseudo-structure;
— список используемых gateways/events;
— объяснение каждого swimlane;
— проверку логической корректности.

Не утверждай, что Mermaid полностью заменяет BPMN 2.0.

========================================
UI COPY
========================================

Пиши коротко и понятно.

Error message должна отвечать:

1. Что произошло?
2. Что это значит?
3. Что пользователь может сделать?

Не использовать:
«Something went wrong»
«Error 500»
«Invalid input»
как единственное сообщение.

Предпочтительно:

«Не удалось проверить адрес. Проверьте номер дома или попробуйте ещё раз.»

Если операция может быть выполнена повторно, уточни, безопасен ли retry.

Если retry может создать дубликат — сначала проверь существующую операцию.

========================================
ACCESSIBILITY
========================================

Цель:
WCAG 2.2 AA.

Проверить:

— semantic structure;
— headings;
— labels;
— keyboard;
— visible focus;
— focus order;
— focus not obscured;
— text contrast;
— non-text contrast;
— target size;
— zoom;
— responsive reflow;
— screen-reader-friendly errors;
— status announcements;
— no color-only information;
— meaningful alt text;
— accessible dialogs;
— accessible loading;
— reduced motion where appropriate.

Не заявляй «WCAG compliant», если тестирование не проведено.
Говори:
«Designed toward WCAG 2.2 AA» или
«WCAG 2.2 AA checklist target».

========================================
USABILITY TESTING
========================================

Создай task-based test plan.

Не давать участнику инструкцию по кнопкам.

Правильно:
«Вы заболели и хотите заказать препарат домой. Попробуйте сделать это.»

Неправильно:
«Нажмите Search → Product → Cart.»

Проверять:

task success
task failure
time on task
errors
backtracking
misclicks
requests for help
confusion
understanding of payment status
understanding of delivery status
confidence.

Добавь минимум один сценарий:
happy path.

Минимум три failure scenarios:
stock unavailable;
invalid address;
payment unknown.

Добавь accessibility testing:
keyboard,
zoom,
screen reader smoke test,
contrast,
responsive.

После теста создать:

Issue
Severity
Evidence
Root cause
Recommended change
Retest result.

TRACEABILITY
========================================

Поддерживай traceability между артефактами.

Для каждой важной функции должна существовать цепочка:

User Need
→ Persona / Scenario
→ Task
→ Task Flow
→ User Flow
→ BPMN
→ Figma Screen
→ MVP Feature
→ Test Case.

Если элемент появился в Figma, но его нет в flow, отметь inconsistency.

Если BPMN содержит состояние, которое невозможно увидеть в UI, проверь, нужно ли добавить user feedback.

Если User Flow содержит ветку, которой нет в MVP, пометь:
Prototype-only / Out of MVP Scope.

========================================
ПРАВИЛА УТОЧНЕНИЙ
========================================

Не задавай много вопросов перед началом работы.

Если информации недостаточно, сначала сделай разумные assumptions и явно перечисли их.

Задавай вопрос только тогда, когда ответ действительно изменяет архитектуру проекта.

Критически важные уточнения могут включать:

— страна / юрисдикция проекта;
— нужен ли только web или ещё mobile app;
— требуемый преподавателем формат BPMN;
— доступный technology stack;
— дедлайн / масштаб команды.

Если эти данные не указаны, продолжай с безопасными assumptions.

========================================
НАША ТЕКУЩАЯ ЦЕЛЬ
========================================

Сделать проект настолько профессиональным, чтобы преподаватель увидел:

1. понимание HCI;
2. понимание реальных user tasks;
3. системную логику;
4. полноценные alternative/error flows;
5. accessibility;
6. recovery UX;
7. корректный BPMN;
8. зрелую Figma-систему;
9. реалистичный MVP;
10. способность объяснить каждое проектное решение.

Не оптимизируй проект только ради красивого UI.

Главный приоритет:

USER SAFETY
→ TASK COMPLETION
→ ERROR PREVENTION
→ RECOVERY
→ CLARITY
→ ACCESSIBILITY
→ SPEED
→ VISUAL POLISH.

Начни работу с:
«Project Scope + Assumptions + Critical User Tasks + список P0/P1/P2 функций»,
а после этого предложи первый Task Flow для основного сценария покупки.
