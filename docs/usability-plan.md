# План проверки удобства и доступности

Это план, а не отчёт о проведённых исследованиях. Интервью, пользовательские тесты и screen-reader тестирование не проводились. Proto-personas — гипотезы для рекрутинга, а не реальные респонденты.

## GOAL / ASSUMPTIONS

Проверить, может ли человек с низкой энергией выполнить покупку, понять unknown payment и выбрать безопасное восстановление. После снятия лимита нужен законченный нативный прототип Figma. Для предварительной оценки текста и последовательности доступен локальный статичный прототип; он не проверяет ввод, backend и настоящую оплату.

## Задания без подсказок по кнопкам

| Сценарий | Задание участнику | Наблюдаемое условие успеха |
|---|---|---|
| A · Happy path | Вы заболели и хотите заказать известный вам товар домой. Попробуйте оформить покупку | Участник сверил вариант товара, заметил полную цену, дошёл до номера заказа |
| B · Stock | Нужного количества товара больше нет. Попробуйте продолжить | Прочитал изменение количества, принял его осознанно или вернулся к поиску |
| C · Address | Сервис не может определить адрес. Что бы вы сделали? | Понял, какое поле исправить; не ожидает потери данных |
| D · Declined | Оплата не завершилась. Попробуйте продолжить покупку | Отличил отказ от успеха и выбрал другой способ |
| E · Unknown | Во время оплаты пропало соединение. Определите, нужно ли платить ещё раз | Не инициировал новый платёж, нашёл проверку прежней операции или помощь |
| F · Network | Каталог не загрузился. Попробуйте продолжить | Нашёл retry, понял сохранение корзины |
| G · Prescription | Товар требует проверки документа. Определите следующий шаг | Не считает автоматическое сообщение одобрением; нашёл проверку/помощь |
| H · Delivery | Доставка задержалась. Разберитесь со статусом и возможностью отмены | Отличил ETA от гарантии; запрос возврата от завершения |

Предлагаемая первая итерация: 5–6 участников, включая людей с разной цифровой уверенностью и сниженным зрением. Это организационное предложение, не статистическое обоснование. Участники думают вслух, модератор не называет кнопки. Не собирать реальные медицинские документы или реквизиты.

## Метрики и шаблон наблюдения

`Participant ID / scenario / success|partial|fail / time-on-task / critical errors / noncritical errors / backtracks / misclicks / help requests / observed confusion / exact quote / confidence 1–5 / understood payment status? / issue severity / design change`.

Порог итерации: ни одного критического ложного понимания unknown как успеха или повода повторно платить; остальные пороги установить после пилота. Нельзя выдавать небольшую выборку за доказательство универсальной доступности.

## Accessibility considerations / checklist target

- Контраст обычного текста ≥4.5:1, крупных надписей ≥3:1; важные границы и focus ≥3:1. Измерять реальные цвета реализации, не только токены.
- Keyboard-only: последовательность Tab, visible focus, Enter/Space, отсутствие ловушек; focus не перекрыт fixed CTA.
- Labels связаны с полями; ошибка у поля через aria-describedby; summary для длинной формы, фокус на первом невалидном поле.
- Status через role=status / aria-live=polite; критическая ошибка через alert без дублирования. Название операции конкретно: «Проверяем адрес», «Проверяем оплату».
- Dialog: доступное имя, перевод/возврат focus, закрытие Escape когда допустимо.
- 200% zoom и reflow при 320 CSS px; основной путь без горизонтального скролла.
- Touch targets ≥48 px у основного CTA; интервалы между действиями.
- Нет информации только цветом, осмысленные alt у информативных изображений, декоративные скрыты.
- Loading не стирает контекст; skeleton не читается как контент. Reduced motion; ожидание не требует анимации.

## OPEN RISKS / QUALITY CHECK

Дизайн не доказывает WCAG compliance. HTML-макеты используют ссылки, а значения полей представлены статично; screen-reader QA полей возможен только после реализации. Нативная композиция и клики Figma ещё не проверены из-за лимита. Результаты тестов следует добавить отдельным файлом после реального проведения; MVP отложен.
