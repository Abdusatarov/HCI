## Task Flow

**Goal:** заказать конкретный безрецептурный товар с доставкой. **Actor:** покупатель. **Preconditions:** известен товар, каталог доступен, продажа допустима, есть запас и доставка. **Trigger:** потребность купить товар домой. **Success:** подтверждённый заказ с номером, доступно отслеживание; доставка — отдельная последующая задача.

Скруглённые терминалы — начало/цель, прямоугольники — действия. Эта диаграмма намеренно линейна; failures не смешаны с task-level действиями. Главные failure points: поиск, остаток/цена, адрес/слот, платёж, сохранение заказа. Полные recovery — в User Flow.

**Self-review:** одна цель, начало/конец, шаги без названий API, подтверждение не опережает ответ. Happy path согласован с User Flow и BPMN.

## User Flow

Скруглённые терминалы — вход/выход; прямоугольник — экран или состояние; ромб — решение, подпись стрелки — условие/действие. Цвет помогает ориентироваться, но смысл всегда продублирован текстом. `Sxx` — стабильные ID экранов для [карты переходов](../docs/screen-map.md) и макетов.

Текстовая карта: Главная → Поиск → Карточка → Корзина → Адрес → Доставка → Оплата → Проверка → Обработка → Подтверждение → Отслеживание. Боковые ветки: пустой поиск, недоступный товар, рецепт, изменение корзины, ошибка адреса, нет доставки, истёкшая сессия, declined, unknown, задержка, отмена и возврат.

**Self-review:** решения имеют все именованные выходы; recoverable состояния ведут к исправлению, ожиданию или помощи; exit явно сохраняет корзину. Unknown имеет безопасную проверку прежней операции, а не кнопку новой оплаты. Ожидание — допустимое состояние; автоматического гарантированного завершения внешних операций модель не обещает.

## BPMN 2.0

Это настоящий BPMN XML с семантикой и Diagram Interchange (DI), не Mermaid-имитация. Модель концептуальная (`isExecutable=false`), запуск в process engine не заявлен. Официальные XSD OMG лежат в `scripts/bpmn-schema`; источник: https://www.omg.org/spec/BPMN/20100501/BPMN20.xsd (и импортируемые схемы того же каталога).

Обзор использует **Call Activity** (толстая рамка с плюсом) и вызывает пять самостоятельных процессов в одном XML. Каждому процессу соответствует отдельная BPMNDiagram. Для чтения достаточно готовых SVG; импорт XML в бесплатный BPMN viewer не обязателен.

### Роли и обозначения

- **User:** покупатель. User Task — действие человека в приложении.
- **Service:** аптека и адаптеры интеграций. Фармацевт — человек, поэтому проверка документа и сборка имеют тип **User Task**, хотя находятся на этой дорожке. Вызов API — **Service Task**, не Script Task.
- **Script/System:** детерминированные локальные операции: проверка обязательных полей, итог, ключ/блокировка, формирование текста статуса. Script Task содержит декларативную спецификацию `text/plain`, не исполняемый backend.
- Внешний платёжный провайдер и курьер показаны отдельными black-box pools в соответствующих детализациях. Message Flow — пунктирный обмен между pools. Sequence Flow остаётся внутри своего процесса.
- Start Event — тонкий круг; End Event — толстый круг. Timer Catch Event — часы и ожидание перед следующей проверкой. Интервал 30 секунд — учебное допущение, не SLA.
- Exclusive Gateway — ромб: выбирается одна именованная ветка. Условия сохранены как FormalExpression, но не привязаны к движку. Parallel Gateway не нужен: реального одновременного fork/join здесь нет.

### Контракт вызовов

Catalog: конец «Корзина сформирована» → `cartReady=true`; выход → false. Eligibility: только «Допуск подтверждён» → `allowed=true`, остановка → false. Checkout: только «Готов к оплате» → `ready=true`, выход → false. Payment: только «Заказ принят» → `confirmed=true`; отказ или отложенная проверка → false. Fulfilment: завершается после подтверждённой доставки или подтверждённой отмены/возврата. Это описание выходных данных модели, не реализованный API.

Псевдоструктура: `Order → Catalog → cartReady? → Eligibility → allowed? → Checkout → ready? → Payment → confirmed? → Fulfilment → end`. Отрицательные результаты не запускают следующий успешный этап. Подробные схемы содержат все task types; в обзорной схеме действия представлены вызовами процессов.

**Self-review:** три дорожки на каждой схеме; правильные типы задач; отдельные внешние pools; все решения подписаны; нет недостижимых узлов и узлов без пути к завершению; declined, unknown и success различаются. Сбой сервера представлен результатом адаптера и recovery-веткой, а не фиктивным успехом. В производственной модели потребуются engine-specific expressions, обработчики технических ошибок и реальные условия компенсации. Бесконечное ожидание внешнего ответа не трактуется как доказательство eventual success.

## Воспроизведение

Требуются Node.js 24, Python 3 + lxml, Chromium, Linux-шрифт DejaVu Sans. Все используемые библиотеки бесплатны.

```sh
PUPPETEER_SKIP_DOWNLOAD=true npm ci
python -m pip install -r scripts/requirements.txt
npm run check
npm run design:export
```

`npm run generate` создаёт XML/DI; `npm run validate` проверяет OMG XSD и структуру; `npm run export` парсит Mermaid и рендерит Mermaid/BPMN в SVG+PNG. Из-за запрета браузера на file:// в рабочей среде экспорт использует бесплатный Node CLI из `scripts/export.mjs`: Mermaid загружается как локальный bundle, BPMN — через bpmn-js, без онлайн-редактора и сетевых запросов при рендере. В CI шрифт и Chromium устанавливаются явно.

SVG открывается в браузере с масштабированием; PNG — для вставки в документ или презентацию. Широкие схемы читать в исходном масштабе, для печати использовать детализации и альбомную ориентацию. GitHub показывает PNG и исходники `.mmd`; полная карта имеет приоритет над размером миниатюры.

[Автоматический отчёт](../docs/validation.json) фиксирует структурную проверку. Визуальный контроль, ограничения и ещё не проведённые проверки описаны в [QA](../docs/quality-review.md).
